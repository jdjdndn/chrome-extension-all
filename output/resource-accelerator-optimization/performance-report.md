## 三、性能指标预测

### 3.1 Core Web Vitals 预期改善

#### LCP (Largest Contentful Paint)

**当前基线**：未启用预加载时，滚动到大图片位置时需要等待加载

**预期改善**：
- ✅ **目标：< 2.5s**
- **预测值**：< 1.8s （改善约 30%）
- **原理**：
  - 滚动感知预加载在用户滚动前提前加载图片
  - 可视区图片优先压缩队列
  - 滚动速度快时自动增加预加载距离（最多 3 屏）
- **验证点**：滚动时无图片空白占位，图片即时显示

#### FID (First Input Delay)

**当前基线**：首次压缩时需要创建 Worker，约 50-100ms 延迟

**预期改善**：
- ✅ **目标：< 100ms**
- **预测值**：< 50ms （改善约 50%）
- **原理**：
  - 页面加载时预创建并预热 Worker
  - Worker 收到微型测试任务完成初始化
  - 首次实际压缩任务无需冷启动
- **验证点**：首次图片压缩无明显延迟

#### CLS (Cumulative Layout Shift)

**当前基线**：src 替换导致图片尺寸临时变化

**预期改善**：
- ✅ **目标：< 0.1**
- **预测值**：< 0.05 （改善约 50%）
- **原理**：
  - 移除 src 替换为透明占位图逻辑
  - 保持原始 src 属性，浏览器保留尺寸
  - 懒加载时不改变 DOM 布局
- **验证点**：滚动时无布局偏移

#### INP (Interaction to Next Paint)

**预期改善**：
- **预测值**：< 150ms
- **原理**：
  - 压缩任务使用优先级队列，避免阻塞主线程
  - 滚动监听使用 passive 事件，不阻塞渲染
  - 预加载策略使用节流，避免频繁计算

## 四、已知局限性

### 4.1 需要实际浏览器环境测量

以下指标需要在真实浏览器环境中进行性能测试：

1. **实际 LCP/FID/CLS 数值**
   - 需要使用 Lighthouse 或 Chrome DevTools Performance 面板
   - 测试不同网络条件（3G/4G/5G）
   - 测试不同设备性能（低端/中端/高端）

2. **滚动 FPS 实测**
   - 需要 Performance 面板录制长滚动场景
   - 测试长页面（> 100 张图片）滚动流畅度

3. **Worker 压缩延迟分布**
   - 测量首次压缩延迟 vs 后续压缩延迟
   - 统计不同尺寸图片的压缩耗时

4. **内存泄漏检测**
   - 长时间运行后的堆快照对比
   - 多次页面切换后的内存增长

### 4.2 需要长期监控的指标

1. **Worker 崩溃率**
   - 统计 `state.stats.workerCrashes`
   - 崩溃率 > 5% 时需要优化 Worker 代码

2. **缓存命中率**
   - 统计 `state._compressCache` 的命中/未命中比例
   - 命中率过低时考虑调整缓存策略

3. **预加载有效率**
   - 统计预加载的图片实际被用户看到的比例
   - 有效率过低时调整预加载距离阈值

4. **带宽消耗**
   - 统计预加载增加的额外带宽
   - 超过阈值时降低预加载距离

### 4.3 边界情况

1. **非常快速的滚动**
   - 瞬间滚动超过 3 屏时，最下方图片可能仍有短暂空白
   - 缓解：最大预加载距离设置为 3 屏

2. **网络突然变差**
   - 预加载过程中网络降级时，已触发的预加载无法取消
   - 缓解：根据网络状态动态调整预加载策略

3. **图片数量极多的页面**
   - > 500 张图片时，内存占用可能超过预期
   - 缓解：缓存 LRU 机制自动清理
