## 设计经验

### 滚动感知预加载
- **问题**：far区域图片替换src为透明占位，滚动时空白
- **方案**：移除src替换，使用原生懒加载 + 滚动速度感知预加载
- **优势**：滚动到位置时图片已存在或正在加载，即时响应
- **注意**：需要根据滚动速度动态调整预加载距离，平衡即时性和带宽消耗

### Worker优化
- **问题**：首次压缩有延迟，Worker可能崩溃
- **方案**：预热Worker、优先级队列、健康检查
- **关键**：预热使用微型测试任务，优先级基于可视状态

## 技术要点

### IntersectionObserver
- 使用非对称rootMargin优化预加载方向
- 快速向下滚动时底部预加载距离更大
- 缓存当前配置避免频繁重建

### 滚动速度检测
- 使用passive事件监听
- 滚动采样间隔100ms
- 停止滚动后重置状态

### Worker健康检查
- 监听onerror事件
- 崩溃时重新创建Worker
- 维护Worker池状态

### Worker动态扩缩容
- **扩容预热**：动态创建Worker后必须立即预热，否则新Worker首次处理任务会有延迟
- **缩容清理**：Worker缩容时必须同步清理预热状态Map，避免状态泄漏
- **索引一致性**：`_workerWarmupStatus`使用worker索引作为key，扩容用`workerCount`，缩容用`_compressorWorkers.length`（pop后的值）

## 性能优化原则

1. **渐进增强**：先确保基础功能，再优化体验
2. **按需加载**：根据用户行为预测，动态调整
3. **资源优先级**：可视区域 > 首屏 > 非关键
4. **内存管理**：限制缓存大小，及时清理

## 代码质量原则

### 字符串字面量完整性
- **问题**：字符串常量缺少闭合引号会导致整个文件语法错误
- **方案**：所有字符串字面量必须正确闭合
- **工具**：使用语法检查工具（ESLint）在提交前捕获此类错误

### 动态代码生成安全
- **问题**：在动态生成的代码中直接插入用户可控的 URL 可能导致 XSS
- **方案**：所有插值到动态代码的字符串必须进行转义处理
  - 单引号 `'` → `\'`
  - 反引号 `` ` `` → `` \` ``
  - 美元符号 `$` → `\$`
- **原则**：不信任任何外部输入，包括看似安全的 URL

### DOM 元素生命周期检查
- **问题**：异步回调执行时元素可能已被移除，导致无效 DOM 操作
- **方案**：所有延迟/异步回调执行前必须检查 `element.isConnected`
- **注意**：`isConnected` 属性是检查元素是否在 DOM 中的标准方法

### 文件编码一致性
- **问题**：GBK/UTF-8 编码不兼容导致中文注释乱码
- **方案**：所有源代码文件统一使用 UTF-8 编码
- **工具**：在编辑器中设置默认编码，使用 git 属性强制编码转换
- **验证**：修改后检查所有中文注释，确保没有乱码字符残留

### 中文注释规范
- **问题**：编码转换时注释中的特殊字符容易丢失语义
- **方案**：注释使用清晰、无歧义的中文，避免使用生僻字或特殊符号
- **检查**：每次提交前使用正则表达式检查是否存在编码损坏的乱码字符

### Fetch 响应状态检查
- **问题**：fetch 请求成功但响应状态码非 2xx 时，直接读取响应体会导致逻辑错误
- **方案**：所有 fetch 调用后必须检查 `response.ok` 或 `response.status`
- **降级**：对于非关键资源（如 CSS 优化），fetch 失败时应记录警告并保留原始资源加载方式
- **注意**：`response.ok` 为 `false` 时不应调用 `response.text()` 或 `response.json()`

### 跨域资源错误处理
- **问题**：跨域 CSS 文件 fetch 可能因 CORS 策略失败，抛出 TypeError
- **方案**：在 catch 块中识别 CORS 错误（`error.name === 'TypeError'` 且包含 'Failed to fetch'）
- **降级**：CORS 错误时记录警告，保持原始样式表不变，避免影响页面样式
- **原则**：资源优化功能应优雅降级，不应阻塞页面正常渲染

### 模块导入完整性检查
- **问题**：新建模块文件后忘记在打包入口导入，导致模块代码不执行
- **方案**：所有新建模块必须在对应的入口文件（如 `content/entries/core.js`）中添加 import 语句
- **验证**：开发完成后检查入口文件是否包含新模块的导入
- **原则**：模块文件存在不等于模块会被执行，必须显式导入

### IIFE 与 ES Module 混合模式
- **问题**：IIFE 模式模块（挂载到 window）不会被 Tree Shaking 优化
- **方案**：优先使用 ES Module 纯导出模式，仅在需要全局访问时挂载到 window
- **注意**：混合模式（IIFE + export）需确保两者 API 一致，避免调用方困惑

## 错误处理与降级机制

### 统一错误处理器模式
- **问题**：各模块独立处理错误，缺乏统一的错误分级、上报和统计机制
- **方案**：创建 ErrorHandler 类，统一管理错误处理流程
  - 错误分级：FATAL（致命）、SEVERE（严重）、MINOR（轻微）
  - 错误上下文：自动收集模块名、操作名、堆栈、URL 等
  - 错误上报：通过 chrome.runtime.sendMessage 上报到 background
  - 错误统计：按模块和级别统计，暴露最近 N 条错误记录
- **原则**：错误处理器应支持模块级处理器注册，实现分层错误处理

### 模块降级机制设计
- **问题**：单个模块失败可能影响整体功能，缺乏优雅降级机制
- **方案**：每个模块实现 gracefulDegradation(reason) 方法
  - 记录降级前状态：保存统计数据用于恢复和调试
  - 禁用高级功能：保留核心功能，关闭复杂特性
  - 清理资源：停止监听器、释放 Worker、恢复拦截方法
  - 使用 NOOP_MODULE 替换：避免空指针错误
- **分级降级**：ImageOptimizer 支持单独禁用压缩或懒加载，实现细粒度降级

### 降级状态追踪
- **问题**：模块降级后状态不可见，无法判断是否可恢复
- **方案**：使用 DegradationManager 记录降级状态
  - 记录降级原因和时间
  - 支持恢复后更新状态
  - 在 getStats() 中暴露降级状态
- **用途**：支持监控面板展示降级状态，触发自动恢复逻辑

### 模块初始化错误处理
- **问题**：模块初始化失败时未捕获异常，导致整个系统不可用
- **方案**：使用 try-catch 包裹每个模块的初始化
  - 捕获异常后调用 errorHandler.handle()
  - 根据错误级别决定是否降级
  - 累计严重错误超过阈值自动降级
- **原则**：单模块失败不应影响其他模块运行
