# 优化报告：mo-executor Skill 使用约束

## 问题分析

### 发现的问题

| 问题 | 来源 | 影响 |
|------|------|------|
| Executor 跳过 Skill 发现流程 | execution-metrics.md 显示 Skill 使用为"代码修改" | 无法复用已有技能，导致重复劳动 |
| Skill 发现流程位置不突出 | mo-executor.md 第40-55行是独立章节 | 容易被忽略 |
| 缺少强制检查机制 | 开发模式流程第79行才进入 Skill 发现 | 执行者可能直接进入编码 |
| "优先用 skill"是软约束 | 第103行写的是"优先用 skill" | 无强制效力 |

### 执行证据

```
# execution-metrics.md 第18行
| mo-executor | a9d1d625d1666ca6e | 代码修改 | ~5m | ✅ | 0 | 完成4个任务，+1715/-670行 |
```

Skill 使用列显示"代码修改"，说明 Executor 没有调用任何 skill，直接使用基础工具完成任务。

## 当前提示词问题

### 问题1：Skill 发现流程位置不突出

**当前提示词（第38-55行）**：
```
## Skill 发现流程

**执行任务前必须检查是否有相关 skill**：

```
Step 1: 检查已有 skill
...
```

**问题**：这是一个独立章节，但没有在开发模式流程中强制前置检查。执行者可能直接跳到"开发模式"章节。

### 问题2：开发模式流程缺少强制检查步骤

**当前提示词（第69-107行）**：
```
## 开发模式

### 1. 读取输入
...

### 2. Skill 发现
...

### 3. 必读文件（按顺序）
...

### 4. 开发原则
...

### 5. 开发实现
...
```

**问题**：Skill 发现在第2步，但没有任何强制检查机制确保执行者不会跳过。

### 问题3：开发原则是软约束

**当前提示词（第99-103行）**：
```
### 4. 开发原则

- **规范是权威** — 所有决策遵循开发规范
- **与已有代码保持风格一致** — 看 1-2 个已完成的模块
- **先理解再动手** — 明确认知目标再写代码
- **优先用 skill** — 有 skill 就用，没有就创建
```

**问题**："优先用 skill"只是原则建议，不是强制约束，容易被忽略。

---

## 优化建议

### 建议1：在文件开头添加强制约束块

**优化后提示词（插入到第24行之后）**：
```
---

## ⚠️ 强制约束：Skill 优先原则

**在执行任何任务前，必须完成以下检查**：

| 检查项 | 动作 | 禁止行为 |
|--------|------|----------|
| 1. 扫描已有 skill | 列出匹配的 skill 名称 | ❌ 直接开始编码 |
| 2. 调用 find-skills | `Skill(skill: "find-skills", args: "{任务关键词}")` | ❌ 跳过此步骤 |
| 3. 没有匹配则创建 | `Skill(skill: "skill-creator", args: "...")` | ❌ 不创建就继续 |
| 4. 使用找到的 skill | `Skill(skill: "{skill名}", args: "...")` | ❌ 使用基础工具替代 |

**违反此约束 = 任务失败**

**正确流程**：
```
检查已有 skill → 调用 find-skills → 无匹配则 skill-creator → 使用 skill → 开始编码
```

**错误示例**：
```
❌ 直接 Read 文件 → Edit 修改 → 完成
```

**正确示例**：
```
✅ 调用 find-skills("图片尺寸处理") → 发现无匹配
   → 调用 skill-creator("image-size-handler") → 创建 skill
   → 使用 skill → 完成
```
```

**改进点**：
1. 放在文件开头，执行者第一时间看到
2. 使用表格形式，清晰列出检查步骤
3. 明确"违反 = 失败"，增加约束力
4. 提供正确/错误示例对比

### 建议2：在开发模式流程中添加前置检查点

**优化后提示词（替换第69-107行）**：
```
## 开发模式

### 0. ⚠️ Skill 检查（强制前置）

**在读取任何文件之前**，必须完成：

```
□ Step 1: 列出已有 skill
   输出示例：已扫描 skills: code-review, tdd-workflow, architect

□ Step 2: 匹配任务类型
   输示例：任务类型=代码修改，匹配 skill: 无

□ Step 3: 调用 find-skills
   输出示例：调用 find-skills("Chrome extension 图片处理") → 无匹配

□ Step 4: 调用 skill-creator（如需要）
   输出示例：调用 skill-creator("image-size-handler")

□ Step 5: 使用 skill
   输出示例：使用 image-size-handler skill
```

**只有完成上述检查后，才能进入 Step 1**。

### 1. 读取输入
...

### 2. 使用已发现的 Skill
...

### 3. 必读文件（按顺序）
...

### 4. 开发实现
...
```

**改进点**：
1. 将 Skill 检查作为 Step 0，强调其前置性
2. 使用检查清单格式（□），便于逐项确认
3. 要求输出示例，强制执行者明确记录每一步
4. 明确"只有完成检查后才能进入 Step 1"

### 建议3：在通知格式中添加 Skill 使用声明

**优化后提示词（修改第125-139行）**：
```
### 7. 通知主智能体（必须）

完成后**必须通知主智能体**：

**开发模式通知**：
```
执行完成
任务：{任务编号}
使用 Skill：{skill名称或"无"}
产出文件：
- {路径1}
- {路径2}
```

**修正模式通知**：
```
修正完成
任务：{任务编号}
使用 Skill：{skill名称或"无"}
已更新 lessons-learned.md
```

**⚠️ 必须声明使用的 Skill。如果声明"无"，需要在经验库中说明原因。**
```

**改进点**：
1. 在通知格式中强制声明 Skill 使用
2. 声明"无"需要说明原因，增加约束力
3. 便于 Observer 追踪 Skill 使用情况

## 预期效果

| 效果 | 改进前 | 改进后 |
|------|--------|--------|
| Skill 发现执行率 | 不确定（可能跳过） | 100%（强制前置） |
| Skill 使用追踪 | 无法追踪 | 通知中强制声明 |
| 新 Skill 创建 | 可能遗漏 | 无匹配时强制创建 |
| Observer 报告质量 | 无法判断 Skill 使用情况 | 可准确记录 |
